## Streams

Results go to stdout; prompts, progress, and diagnostics go to stderr, so piping stdout stays useful. `coolship open --print | pbcopy` copies only the URL, and `coolship deploy > result.txt` keeps the status lines and build log on the terminal while the final result lands in the file. When the stage checklist is drawn, a finished deployment's result on stdout is its URL alone: the checklist's summary line on stderr already names the application, the environment, and the time taken.

## JSON

`--format json` prints one result object per command. The shapes are documented on each command page, and every result that names an application carries the same `target` object (see the [command reference](/docs/commands)). `logs --format json` prints newline-delimited events, one object per line, for a single snapshot and when following. JSON mode never mixes human progress into stdout, and JSON output is never styled.

Values that may be secrets are masked in JSON as well, unless `--show-values` is given. The token never appears in any output; at debug verbosity only its last four characters are shown.

## Styling

Human output is colored only when the stream it goes to is a terminal, and each stream is decided on its own, so `coolship status | cat` prints plain text while a prompt on the terminal is still styled. Styled elements are `doctor` markers, deployment statuses, `Warning:` and `Error:` prefixes, prompt questions, `env diff` markers, and key/value labels, using plain ANSI sequences.

Set [`NO_COLOR`](https://no-color.org) or pass `--no-color` to turn styling off everywhere; `TERM=dumb` and `CI` do the same. JSON output and the server's logs are never styled.

## Checklists

In a terminal at normal verbosity, `deploy`, `start`, `restart`, and `preview` draw a deployment's stages as a checklist, and `login`, `link`, `init`, `stop`, and `env push` draw their steps the same way, redrawn in place on stderr as things happen. Every row reads the same: a spinner and elapsed time on what is open, `✓` and a duration on what finished, `✗` on what failed, `–` on what did not run, with why after the name (`skipped (cached image)` for a build Coolify reused an image for, `not used` for the rolling update a Compose deployment, a preview, or an application with mapped ports does not have), `…` on what was still open when observation stopped, and a dim name on what was not reached. Warnings, and the build log with `--logs`, print above the checklist and stay. When a checklist ends, the rows it drew are erased and the final checklist is printed once in their place, where it stays; a finished deployment's URL follows on stdout, and a failed deployment's build log and deployment page follow on stderr. Off a terminal, with `--format json`, or above normal verbosity nothing is drawn: each transition is one plain line on stderr.

## Verbosity

A run shows one of three levels. **Normal** is the default; for now, results name applications and deployments with their UUIDs at every level. **Verbose** adds one line on stderr for every request Coolship sends to Coolify: the method, the URL, the status (or `no response`), the time taken, and `(retry N)` for a retried read. **Debug** adds each request's and response's headers and bodies under that line, curl-style, with the token masked to its last four characters, secret values in bodies redacted, and control characters removed.

```text
$ coolship status --verbose
GET https://coolify.example.com/api/v1/applications/mm4c0zpbrzx8z96t0qiw3tff 200 OK 84ms
…
```

The level comes from the first of these that is set:

1. `--debug`, then `--verbose` (both long-only; `-v` is the version);
2. `COOLSHIP_VERBOSITY=normal|verbose|debug`, for CI; any other value is invalid input;
3. the `verbosity` key of the [preferences file](/docs/commands/config#preferences);
4. normal.

Verbose and debug output goes to stderr only, so stdout and `--format json` are the same at every level. At verbose, identical requests in a row, such as the poll of a deployment every two seconds, print one line, and the repeats are summed up in a second line when a different request comes or the command ends: `GET https://coolify.example.com/api/v1/deployments/abc 200 OK ×11 more (last 45ms)`. Retries and requests that got no response always print. Debug prints every request. Above normal, `deploy`, `start`, `restart`, and `preview` stream the build log unless `--no-logs` or the `build_logs` preference says otherwise (then it is held back and printed in full only if the deployment fails), and no spinner or stage checklist is drawn, so the request lines are never overwritten; the plain stage and status lines print instead, each finished stage with its duration and each status line with the time since the deployment was queued. Debug output redacts secrets in request and response bodies: in JSON, the values of variables (`value`, `real_value`) and of any field whose name contains `secret`, `password`, `private_key`, `token`, or `api_key` are shown as `[redacted]`, so the variable values `env set`, `env push`, and `env pull` carry and the private key `init --create-deploy-key` registers stay out of it. A body that starts like JSON but cannot be parsed is withheld. Set `COOLSHIP_DEBUG_UNREDACTED=1` to see bodies exactly as sent and received; the token stays masked either way. Redaction goes by field name and cannot catch a secret inside another field, such as a compose file, so keep debug output out of shared CI logs all the same.

## Prompts

Commands that change something show their plan and ask for confirmation on stderr. When stdin is not a terminal there is no prompt: pass `--yes` (`--replace` for `link`) or the command refuses. `link` and `init` prompt for a choice only when it is genuinely ambiguous; `q` cancels a selection.

## Hints

In a terminal, a few commands end with dimmed next steps on stderr. After `link` and `init`, Coolship reads the application once more and suggests at most three commands from what it finds: `env push` when a local `.env` sets variables the application does not have yet, `domain set` when it has no domain or only the one Coolify generated (`domain set SERVICE=URL` for a Compose application), then `deploy` when it was never deployed, or `logs` and `open` when it was:

```text
$ coolship link
…
Next:
  coolship env push        send the 3 variables in .env to Coolify
  coolship domain set URL  give the application a domain
  coolship deploy          build and start it
```

`init` asks `Deploy now? [y/N]` instead of suggesting `deploy`. Enter answers no; `y` runs `coolship deploy` for the same target, with its checklist. With `--deploy` there is no question. `deployments` with nothing to list prints `No deployments yet. Next: coolship deploy`, and a mistyped command, context, or target name gets a `(did you mean …?)` in its error.

### Fixing a failed command

When a command fails in a way Coolship can set right, the error is printed as usual and a fix is offered below it:

| Failure | Offer |
| --- | --- |
| [`no_credentials`](/docs/platform/errors#no_credentials) | Run `coolship login` here. |
| [`unauthorized`](/docs/platform/errors#unauthorized) | Log in to the same context again with a new token. |
| [`not_linked`](/docs/platform/errors#not_linked) | Choose `coolship link`, `coolship init`, or leave. |
| [`unknown_context`](/docs/platform/errors#unknown_context), [`no_default_context`](/docs/platform/errors#no_default_context) | Pick a saved context for this run, log in, or leave. |
| `api_disabled`, `ip_not_allowed` | Open Settings, Advanced on the instance in a browser. |
| `missing_permissions`, `token_exceeds_role` | Open Keys & Tokens, API tokens on the instance, then log in with the new token. |

```text
$ coolship status
Error [no_credentials]: No Coolify credentials at /home/you/.config/coolify/config.json
Hint: Run coolship login to save a Coolify URL and API token, or set COOLSHIP_URL and COOLSHIP_TOKEN.
Docs: https://coolship.itrocas.com/docs/platform/errors#no_credentials
Coolship can run coolship login here, then run coolship status again.
Set it up now? [Y/n]
```

Enter accepts. Once the fix is done the command runs again with the same arguments: at once when it only reads, and after `Continue with coolship deploy? [Y/n]` when it changes something (`deploy`, `preview`, `cancel`, `start`, `stop`, `restart`, `env push`, `domain set`), or when a page was opened and a person has to change the setting first. Declining, or leaving the fix, ends with the original error and its exit code. A command that fails again is reported as usual, with no second offer. No fix is offered for `login`, `logout`, `unlink`, `config`, or `alias`, and no login is offered while `COOLSHIP_URL` or `COOLSHIP_TOKEN` is set, since those win over any saved context.

### Turning hints off

Hints, the `Deploy now?` question, and fix offers are never shown with `--format json`, in CI, or when stdin or stderr is not a terminal. To turn all three off in a terminal too, set the `hints` [preference](/docs/commands/config#preferences):

```bash
coolship config set hints false
```

`coolship config set hints true` turns them back on. The [update notice](/docs/commands/config#update-notice) has its own `update_check` preference.

## Exit codes

| Code  | Meaning                                                   |
| ----- | --------------------------------------------------------- |
| `0`   | Success.                                                  |
| `1`   | The operation failed.                                     |
| `2`   | Invalid input, configuration, or selection.               |
| `130` | Interrupted.                                              |

Errors are printed once, on stderr, and classified into these codes at the process boundary; see [Errors](#errors) for what is printed. Some commands give a code a specific meaning: `doctor` exits `1` when any check fails, `env diff --exit-code` exits `1` when there are differences, and `dev` exits with the child process's status.

## Errors

A failure Coolship recognizes is printed with its [error code](/docs/platform/errors), a hint, and a documentation link, on stderr:

```text
$ coolship deploy
Error [missing_permissions]: Coolify POST /deploy: HTTP 403 Forbidden: Missing required permissions: deploy
Hint: The API token lacks a permission this command needs. Create a token with read, write, and deploy (build logs and secret values also need read:sensitive) under Keys & Tokens, API tokens, then run coolship login.
Docs: https://coolify.io/docs/api/permissions
```

The link goes to Coolify's documentation when the fix is in Coolify's setup, such as API access or token permissions, and to the [error codes](/docs/platform/errors) page otherwise. Any other failure keeps a single `Error:` line with no code, hint, or link. An interrupt prints `Interrupted`, and a declined confirmation prints `Cancelled`.

With `--format json`, the text above still goes to stderr, and stdout also gets one error object on its own line:

```json
{"error":{"code":"missing_permissions","message":"Coolify POST /deploy: HTTP 403 Forbidden: Missing required permissions: deploy","hint":"The API token lacks …","docs_url":"https://coolify.io/docs/api/permissions"}}
```

All four fields are always present. A failure without a catalog entry gets a generic code (`invalid_input`, `unclassified`, `checks_failed`, `interrupted`, or `cancelled`), with an empty `hint` and `docs_url`. The object comes after anything the command already printed, so the events of `logs --format json` are followed by it: read the last line, or the object that has an `error` key. A command whose result already says what failed prints that result and no error object, so stdout stays one JSON value: `doctor`'s checks, with `"failed": true`, and a deployment that failed or timed out after it was queued, with its last status. A command that exits with a child process's status (`dev`, `env diff --exit-code`) prints no object. The exit code is the same in both formats, so a script can still check it first.
